## 前言

这个项目从 2026 年 5 月 25 日正式进入密集开发期，到 6 月 7 日角色管理模块落地，历时约两周。系统定位不是传统 CRM 的"电子化台账"，而是以 **AI 智能体为核心驱动力** 的 ToB 销售作战系统——把销售方法论、决策链分析、停滞预警、知识库赋能直接做进业务流程，让系统成为销售的"参谋"而不是"账本"。

当前版本 **V2.3**，已从一个零测试、零 lint、无 git 的脚本集合，演进为具备完整质量防线的 monorepo 工程。

## 一、开发历程、经验与收获

### Phase 0 — 架构骨架（5 月 25 日）

**核心动作：**
- 目录重构：拆分为 `apps/web`（React + Vite）和 `apps/api`（Fastify + Prisma）
- Agent 后端骨架：意图路由、编排器、工具注册
- 前端交互体系：React Router、表单组件、API 客户端（`extractPayload` 拆包契约）
- Agent 核心架构重设计：ReAct 推理循环、上下文构建器、响应构建器

**关键收获：**  
一开始就确立了"**前后端同构的 API 信封协议**"（`{ success, data, error }`），虽然后期暴露了隐式契约的理解成本，但整体统一性为后续调试和错误处理打下了基础。

---

### Phase 1 — 知识库与 UI 体验（5 月 26 日）

**核心动作：**
- 知识库 Embedding 调试收尾
- 文件上传修复（Multipart + MinIO）
- 9 项 UI/UX 改进

**关键收获：**  
文件上传这类"边缘功能"往往是用户体验的断点。MinIO + 预签名 URL 的链路一旦跑通，后续 AI 分析、文档录入、拜访录音等多个功能都能复用。

---

### Phase 2 — 智能体闭环：9 个缺口全部闭合（5 月 27 日）

这是项目第一次完整的"拼图验收"。

| 缺口 | 内容 | 业务价值 |
|------|------|----------|
| 缺口 1 | 决策链模型（联系人 decisionRole + 项目 decisionMap） | 让销售知道"谁说了算、谁有否决权" |
| 缺口 2 | 销售方法论知识库（9 里程碑标准动作/卡点/推进技巧） | 把组织经验变成系统能力 |
| 缺口 3 | 主动智能（dailyScan 巡检、停滞检测） | 从"人找事"变成"事找人" |
| 缺口 4 | 自然语言→结构化数据闭环 | 销售说话，系统自动录入 |
| 缺口 5 | 客户 360 视图 | 跨模块聚合客户全貌 |
| 缺口 6 | 销售流程推进指引 | 每个里程碑该做什么，系统直接提示 |
| 缺口 7 | 工具执行→业务操作闭环 | AI 不只建议，还能直接执行 |
| 缺口 8 | 产品/竞品知识库 | 话术生成、异议处理有据可依 |
| 缺口 9 | 对话回复质量 | Markdown 渲染、格式规范 |

**关键收获：**  
"闭合缺口"比"增加功能"更重要。每个缺口都是"AI 知道但系统做不到"的断点，闭合后才能形成真正的业务闭环。

### Phase 3 — 录入体验（5 月 30 日）

- 文件上传边界判断
- **AI 自动录入预览（A6）**：语音/文本 → 结构化提取 → 预览确认 → 批量写入

**关键收获：**  
引入了 `dryRun` 模式和 `enrollPreview` 机制——AI 提取的结果先给人看，确认后再写入。这是从"AI 自动执行"到"AI 辅助决策"的关键设计，既提效又避险。

---

### Phase 4 — 数据层整改（6 月 1 日）

- Prisma 字段名全局修复（`snake_case` → `camelCase`）
- 销售方法论角色对齐（5 角色 → 3 角色：决策者/评估者/引导者）
- 产品介绍功能核对

**关键收获：**  
技术债会复利。字段命名不一致导致前后端、AI 写回、数据库查询多处对不上，一次性整改虽然痛苦，但后续新增功能的维护成本显著下降。

---

### Phase 5 — 文档分析 + 审查体系（6 月 2 日）

- 反编造校验整改（guardrails.js 增加 sourceType）
- Markdown 专用分析器 + 表格解析器
- 批量录入接口 `/api/agent/enroll-bulk`
- 上下文长度限制修复
- 对话持久化修复
- **V2.3 四层自动化审查体系落地**

**关键收获：**  
"Baseline 机制"是 legacy 项目引入 lint 的唯一可行路径。首次扫描 86 个违规，如果全部阻断，commit 永远不可能成功；计入基线、只拦截新增，才能让质量防线和业务发展并行。

---

### Phase 6 — 故障排查与修复（6 月 4 日）

一日内修复 5 个生产级故障：

1. **模型测试"链接失败"** — `extractPayload` 隐式契约问题
2. **小销助手完全不可用** — 缺失 `getAIConfig` import
3. **线索转化 400 错误** — 空 POST body
4. **AI 诊断 INTERNAL_ERROR** — DeepSeek + AI SDK tools 不兼容
5. **拜访表单显示商机 ID** — 前端传参不匹配

**关键收获：**  
这一天沉淀了两条核心记忆：
- **"兼容 OpenAI API" ≠ 所有功能都兼容**，tools/function calling 必须实测
- **缺失 import 必须用静态类型检查拦截**，不能依赖运行时

---

### Phase 7 — 拜访模块修复 + 页面增强（6 月 6 日）

- 修复 `visits.controller.ts` 语法错误（stray `}` 阻塞启动）
- 修复 `analyzeVisit` 写回逻辑与 Schema 不匹配
- AI SDK v6 `maxTokens` → `maxOutputTokens` 兼容性（4 文件）
- 修复 Task 创建缺失 `ownerId`
- 项目全生命周期视图 + 时间线 UI
- 工作台/报表拆分
- 公海池认领入口增强

**关键收获：**  
"Schema 对齐"是 AI 写回场景的最高频 bug。AI 输出结构、Zod Schema、Prisma 模型、前端展示，四层必须同步维护，任一层的复制粘贴都会导致静默失效。

---

### Phase 8 — 角色管理与权限体系（6 月 7 日）

- 5 静态角色（SUPER_ADMIN / TENANT_ADMIN / DEPT_HEAD / SALES / VIEWER）
- RBAC Plugin + 用户管理 API（列表/更新/删除）
- 前端 `useHasRole` / `useIsAdmin` / `useCanAssign` 权限 hooks
- `<RequireRole>` 路由守卫
- 侧边栏按角色过滤
- 设置页成员管理弹窗（角色编辑、状态切换、删除）
- **修复 `useAuthUser` 潜伏的 double-extraction bug**

**关键收获：**  
这个 bug 堪称典型：表面上是权限体系失效，根因是两个月前 `get<T>()` 拆包契约被 hook 作者误解。它说明：**新增功能依赖旧 Hook 时，必须先验证旧 Hook 真的返回什么。**

---

### 沉淀下来的核心经验

**可靠性（8 条）：**
1. 路由层降级优于执行层报错
2. JS 空对象 `{}` 不是 falsy
3. 修改后端代码后必须重启进程
4. 工作流 inputSchema 必须与 extractParams 严格对应
5. 前端集合属性必须设默认值 `[]`
6. 方法重构时必须全局搜索调用点
7. 测试要覆盖"意图正确但参数不全"的降级路径
8. 删除端点前先保留兼容 stub

**第三方兼容性（5 条）：**
1. "兼容 OpenAI API" ≠ 所有功能兼容
2. `extractPayload` 已拆包，禁止再取 `.data`
3. 空 POST body 会导致 Fastify 400
4. 500 错误信息被吞是调试灾难
5. 缺失 import 必须被静态检查拦截

## 四、软件的优势特点

### 1. 业务方法论内嵌，不是外挂

市面上大多数 CRM 是"空盒子"，销售流程需要企业自己定义和训练。这个系统直接把 **9 里程碑 Pipeline**、**三角色决策链**、**SPIN/LSCPA 等方法论**做进了数据模型和 AI prompt 里。销售不需要懂方法论，系统会在正确的节点提示正确的动作。

### 2. AI 不是聊天框，是业务操作员

小销助手不只是回答问题，它能：
- 从聊天记录里提取线索信息并预览录入
- 分析拜访录音并自动更新商机状态
- 检测项目停滞并主动预警
- 直接执行"创建任务""推进里程碑""分配客户"等操作

这是"**Copilot + Agent**"的混合形态：日常是参谋，关键节点能动手。

### 3. 数据完整性与幻觉防控并重

- **反编造校验**：AI 没有可靠来源时，不会捏造联系人、预算、决策链
- **dryRun 模式**：AI 批量写回前先给人预览确认
- **tenant-guard 代理**：所有数据查询自动注入租户隔离，杜绝跨租户数据泄露
- **Schema 同步检查**：工具 inputSchema 与 Prisma 模型一致性被 linter 监控

### 4. 权限体系贴合 ToB 组织

5 个静态角色覆盖了从平台管理员到只读用户的完整光谱：
- SUPER_ADMIN：跨租户平台管理
- TENANT_ADMIN：租户内最高权限，可管理成员和配置
- DEPT_HEAD：部门主管，管理部门数据、分配客户
- SALES：一线销售，跟进自己的线索和商机
- VIEWER：只读用户，查看数据但不可编辑

菜单、路由、页面元素三级隐藏，权限失效不会只是"按钮点不了"，而是"根本看不到"。

### 5. 工程化质量防线

V2.3 建立的四层审查体系，让这个项目从"靠人盯"变成"靠门禁拦"：
- 硬编码里程碑会被 ESLint 拦截
- 数据隔离缺失会被 tenant-guard 拦截
- Schema 不一致会被 schema-sync 拦截
- 类型错误会被 `tsc --noEmit` 拦截

对于快速迭代的 AI 项目，这比单纯堆功能更有长期价值。

## 五、做得不错的地方

### 1. 架构决策有定力

- **静态角色而非动态 RBAC**：用户明确要求"先解决当前 5 个角色"时，没有为了追求"更灵活"而引入 Role/Permission 矩阵，选择了最小可行方案。
- **单租户模式先行**：在多租户功能未成熟前，果断把新注册收敛到默认租户，避免了"用户互相看不见"的混乱。
- **共享包 `@ai-sales/shared`**：前后端共用常量、类型、Schema，避免了字符串硬编码和版本不一致。

### 2. 问题排查有方法论

从多次故障排查中可以看出，已经形成稳定模式：
- **先定位核心矛盾** → 再评估必要性 → 再给方案让用户决策
- 不轻易假设"旧代码是对的"（`useAuthUser` bug 的排查就是典型案例）
- 善用 curl 直接验证后端，缩小"前端问题"还是"后端问题"的范围

### 3. 对"隐式契约"有清醒认识

`extractPayload` 拆包、空 POST body、DeepSeek tools 兼容性，这些问题本质上都是"**我以为你知道**"的契约问题。项目已经开始系统性地把它们变成显式规则、linter 检查、文档记忆，这是工程成熟度提升的标志。

### 4. 质量投入前置

在功能还在快速增加的阶段，就投入了：
- ESLint 自定义规则
- 架构合规 Linter
- 测试金字塔
- CI/CD 流水线
- TypeScript 渐进式类型化

这不是"先做功能再补质量"的惯性路径，而是承认 AI 项目的不确定性高，必须用工具和流程来降低人脑负担。

### 5. 业务理解与技术实现对齐

ToB 销售不是简单的"客户-商机-订单"三表结构。系统里能看到很多贴合业务的设计：
- **决策链地图**而不是"联系人列表"
- **九里程碑**而不是"销售阶段"
- **健康度雷达**而不是"优先级下拉框"
- **停滞预警**而不是"手动筛选"
- **公海池认领**而不是"分配按钮"

这些设计说明技术实现是在服务业务逻辑，而不是让业务逻辑去迁就技术约束。

## 结语

这个系统目前的状态是：**核心功能已跑通，质量防线已建立，但仍有打磨空间。**

短期来看，最需要关注的是：
1. **前端 UI 的端到端验证**（很多功能后端已通，但前端交互细节需要真实用户场景打磨）
2. **遗留 tenant-guard 基线的清理**（5 个高优违规）
3. **AI 回复的可解释性**（为什么 AI 给出了这个建议？依据是什么？）
4. **模型 Provider 适配层**（DeepSeek 不走 OpenAI 兼容模式）

整体而言，从 0 到 V2.3 的这两周，节奏紧凑、决策务实、问题定位清晰。系统的地基打得比很多同类产品更稳，接下来的重点是**在保持质量的前提下，把 AI 的"聪明"真正转化为销售的"省力"**。
