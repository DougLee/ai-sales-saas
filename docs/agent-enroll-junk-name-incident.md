# 小销入库事故复盘：「上边提到的前三个」被当客户名建库

> 记录时间：2026-08-15
> 关联 issue：[#21](https://github.com/DougLee/ai-sales-saas/issues/21)（已关闭）
> 修复 commit：`4babc36`

## 1. 事故现象

用户在小销对话中让 AI 推荐了邯郸市目标客户清单，随后下达指令：

> 把上边提到的前三个客户入库

两个问题同时发生：

1. **数据污染**：`Company` 表真实创建了名称为 **「上边提到的前三个」** 的客户记录（`source=ai_recommendation`，`dataConfidence=medium`，落入公海池）
2. **幻觉回复**：小销没有确认入库结果，而是输出了一整套「进入 CRM 后台 → 批量导入 → 下载模板 → 粘贴表格」的手动导入教程——系统明明已经执行了入库动作，却在教用户绕开系统手动干

## 2. 根因分析

### 2.1 缺陷一：序数解析不认「前/后 N 个」

`apps/api/src/agents/skills/crm/customer-enroll.util.ts` 的 `resolveEnrollTargets` 三级解析顺序是：序号 → 全部 → 名称。

序号正则原本只有：

```ts
// 只认「第 N 个/条/家/所/校/院/位/名」
const ordMatch = msg.match(/第\s*([一二三四五六七八九十\d]+)\s*[个条名家位所校院]/)
```

「**前**三个」没有「第」字，序号级不命中；「全部」级的关键词（全部/都入库/这些）也不命中；于是整句落入第三级**名称兜底**：

```ts
// 惰性捕获：「把(上边提到的前三个)(客户)入库」→ ba[1] = "上边提到的前三个"
const ba = msg.match(/把\s*([一-龥A-Za-z0-9·]{2,30}?)(?:公司|学校|学院|大学|客户|机构)?\s*(?:入库|入公海|建档|加进)/)
```

原有的 `ordinalLike` 过滤器只防「第X家」形态（`^第\s*N\s*[量词]?$`），防不住指示代词短语。「上边提到的前三个」通过过滤 → 与候选匹配失败 → `origin: 'name'` 按新客户名直建 → `lead-action` 入库成功。

### 2.2 缺陷二：system prompt 尾部指令被模型无视

`chat.handler.ts` 中入库结果注入方式：

```ts
system += `\n\n【入库结果】${enrollNote}\n请用一两句话向用户确认...`  // 追加在末尾
```

DeepSeek-V3.2 在长 system prompt（业务框架 + skill 结果 + 历史上下文）下无视了尾部这段指令，按通用 CRM 助手人设自由发挥出导入教程。**执行层做了正确的事，表达层把用户带偏了。**

### 2.3 链路图

```
用户指令 ──→ intent-rules /入库/ 命中 customer_enroll ✅
        ──→ resolveEnrollTargets
              ├─ 序号级：「前三个」不匹配「第N个」 ✗
              ├─ 全部级：无关键词 ✗
              └─ 名称级：捕获「上边提到的前三个」→ 守卫失效 💥
        ──→ lead-action 建库（垃圾名）💥
        ──→ enrollNote 注入 prompt 尾部 → LLM 无视 → 输出教程 💥
```

## 3. 修复方案（4babc36）

### 3.1 序数增强：前/后/第 三态

```ts
// 前 = 头 N 个 slice(0,n)；后 = 末 N 个 slice(-n)；第 = 第 N 个 [n-1]
const ordMatch = msg.match(/(第|前|后)\s*([一二两三四五六七八九十\d]+)\s*[个条名家位所校院]/)
```

- 补「**两**」（后两个）进数字映射与字符类
- 超出候选数时**不入库**并返回可解释原因（「上一轮只推荐了 4 个，没有前 5 个」）

### 3.2 垃圾名称守卫 JUNK_NAME_RE

任何来源（引号/书名号/把X入库捕获）的候选名，入库前必须过守卫：

```ts
const JUNK_NAME_RE =
  /(?:第|前|后)\s*[一二两三四五六七八九十\d]+\s*[个条名家位所校位]?$|  // 序数短语
   ^上边|^上面|^前面|^刚才|^之前|^上述|^前文|^这家|^那个|               // 指示代词
   提到|自动|全部|这些|几个|                                            // 动作碎片
   [个条家些]$/                                                        // 量词结尾
```

守卫命中即拒绝建库；名称兜底彻底失败时返回引导话术（「请先让我推荐目标客户，或直接给出客户名」），而不是猜测。

### 3.3 顺带修复：机构后缀整体捕获

老正则的 `(?:公司|大学|学院…)?` 是捕获组外的可选项，「把开封大学入库」会把「大学」吃掉只留「开封」入库。改为把后缀并入捕获组，名称完整。

### 3.4 回复强制：enrollNote 移到 system prompt 首部

```ts
system =
  `\n【入库指令执行结果——你的回复必须且只能基于此】\n${enrollNote}\n` +
  `规则：1) 只用一两句话确认入库结果；2) 只复述结果里真实出现的客户名，一个都不能编造；` +
  `3) 结果说明未入库/未识别时如实转告并给出指令示例；` +
  `4) 严禁输出"批量导入教程/模板/后台操作步骤"——入库由系统直接完成。\n\n` + system
```

首部位置 + 明确禁止项，压过业务框架人设的长尾干扰。

### 3.5 回归测试

`tests/unit/agents/skills/customer-enroll.test.ts`，11 个用例，**首条即本次原话**：

```ts
it('前三个 = 头 3 个候选（本次事故用例）', () => {
  const { targets } = resolveEnrollTargets('把上边提到的前三个客户入库', cands)
  expect(targets.map((t) => t.name)).toEqual(['邯郸市中心医院', '河北工程大学', '邯郸学院'])
})
```

另有：前3家/第三个/后两个/超出候选数/指示代词拒绝/动作碎片拒绝/引号匹配/无引号直建等。

### 3.6 数据清理

垃圾记录 `cmstpo8nx0007zzjgjztiapfi` 按系统口径**软删除**（`deletedAt` 置位，保留审计痕迹）。

## 4. 设计反思

1. **自然语言指令解析的兜底顺序 = 安全等级顺序**。名称直建是权限最大的一级（允许任意字符串入库），却排在最后当兜底——兜底恰恰收到的是最难解析的输入。凡兜底路径必须过最强的守卫，否则它就是垃圾数据的后门。
2. **正则规则要用真实语料养**。「前 N 个」「后 N 个」「前两家」是中文口语的最常见说法，第一版只写了「第 N 个」说明规则是从模板想出来的，不是从用户话术里长出来的。后续新增解析规则时，先收集 10 句真实用户表达再写正则。
3. **写操作的结果要在 prompt 里“插队”**。追加在 system 尾部的指令在长上下文里会被淹没；凡是「系统已经做了 X」的事实，必须置于 prompt 最高优先级位置，且附带禁止项（禁止教程、禁止编造），否则模型会用预训练里的通用知识覆盖系统事实。
4. **两处独立缺陷会互相掩盖**：如果回复正确确认了「已创建客户：上边提到的前三个」，用户当场就能发现名字不对；如果入库被守卫拦住，教程式回复也只是废话。两个都坏了才造成“数据库悄悄进垃圾 + 用户被引去手动操作”的双重伤害。测试要覆盖完整链路，而不是只测解析函数。
